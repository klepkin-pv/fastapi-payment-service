# Проект: раскладка, стек, структура кода

Читать перед первой реализацией в сессии. Здесь инварианты проекта: отступать можно только по явной просьбе пользователя или через запись в `DECISIONS.md`.

---

## Раскладка

```
docker/            ← Dockerfile'ы, compose, конфиги окружений
database/          ← миграции, схемы, сиды, SQL
backend/           ← сервис API
frontend/          ← клиент
.gitignore
.dockerignore
README.md
local.run.*        ← локальный запуск
```

Создаётся только то, что реально есть в проекте: пустых каталогов «на будущее» не бывает. Появился новый сервис — новая папка рядом с существующими по тому же шаблону.

**Сервисы изолированы.** Код сервиса целиком лежит в своей папке: свой манифест зависимостей, свои тесты, свои настройки. Один сервис не импортирует внутренности другого — только через явный контракт: HTTP-эндпоинт, очередь, общий пакет. Появился импорт `../backend/src/...` из фронтенда — это ошибка, а не удобство.

**Контракты описываются до реализации:** эндпоинт, формат, ошибки. Место стыка — план `.plans/`, а не догадки в коде. Формат на границе версионируется, если его читает кто-то кроме автора. Breaking change в контракте — это решение, а не деталь: спрашивай.

Внутри сервиса — группировка по фичам, а не по типам файлов:

```
frontend/
└── src/
    ├── features/
    │   ├── contacts/          ← фича целиком: ui, логика, типы, тесты
    │   │   ├── ui/
    │   │   ├── model/
    │   │   └── api/
    │   └── deals/
    └── shared/                ← только то, что реально общее
        ├── ui/                ← базовые кнопки, поля, layout
        └── lib/               ← утилиты без бизнес-смысла
```

Не бывает общих папок `components/`, `services/`, `types/`, куда сваливается всё подряд.

## Локальный запуск и Docker

Локальный запуск не должен отличаться от докерного. Один и тот же код, одни и те же переменные окружения, одни и те же точки входа — отличается только способ сборки.

- `local.run.*` — тонкая обёртка: поднимает то же приложение теми же командами. Логики внутри нет, машинозависимого хлама тоже. Файл коммитится: это часть настройки проекта
- Конфигурация — только через переменные окружения. Значения для локали — в `.env.example`, секреты — в `.env` (он в `.gitignore`)
- **В бизнес-логике нет ветвлений «если локально».** Драйверы, пути, хосты и порты выбираются конфигом, а не условием в коде
- Порты и имена сервисов совпадают с docker compose. Отличается — расхождение фиксируется в `WORKING-CONTEXT.md`
- Схема данных накатывается теми же миграциями из `database/`, что и на проде. Отдельных «локальных» миграций не существует

**База данных.** По умолчанию локально поднимается тот же движок, что и в проде, через compose — это даёт полную идентичность. SQLite локально допустим как осознанное упрощение, но только при трёх условиях: доступ идёт через тот же слой данных (тот же ORM, те же запросы), специфика SQLite заперта в адаптере и не протекает в бизнес-логику, расхождение записано в `WORKING-CONTEXT.md`. Как только появился SQL-запрос «под SQLite» в общем коде — упрощение отменяется.

## Стек — инвариант

Стек выбирается **один раз, на старте**: агент предлагает исходя из задачи, пользователь подтверждает или меняет, итог записывается в `WORKING-CONTEXT.md`. Дальше он не меняется.

**Сменой стека считается** (требует согласования): новый фреймворк, ORM, база данных, сборщик, тест-раннер; замена библиотеки на аналог; крупная зависимость, диктующая структуру кода (роутер, стейт-менеджер, UI-кит); смена менеджера пакетов; мажорное обновление фреймворка.

**Не считается**, но всё равно не делается молча: мелкая утилита без влияния на архитектуру — предложи одной строкой и получи ответ.

Порядок добавления зависимости:

1. Проверь, нет ли уже решения в стеке: нужна библиотека — сначала `explorer` поищет, не закрыт ли вопрос имеющимися средствами
2. Объясни, зачем она и что будет, если обойтись
3. Получи подтверждение
4. Архитектурное решение — запиши в `DECISIONS.md`
5. Ставь в тот сервис, которому она нужна, а не в корень проекта

Версии фиксируются lock-файлом, он коммитится. Обновление зависимостей — отдельная задача, а не побочный эффект другой правки.

## Файлы и компоненты

- **Один компонент — один файл.** Компонент, класс, модуль — отдельный файл, названный так же, как то, что в нём лежит. В одном файле не живут два независимых компонента
- Рядом с компонентом — его типы, стили и тесты. Общих папок `types/`, `styles/`, `helpers/` не заводится
- Папка растёт быстрее пяти файлов — дели на подпапки по смыслу
- Функция до ~50 строк, файл до ~400. Перевалил — предложи разделить, не молчи

## Переиспользование вместо дублирования

**Перед созданием нового — поищи существующее.** Нужен компонент кнопки, форматтер даты, валидатор — сначала `explorer` ищет, нет ли уже такого. Дубликат, созданный второй раз, живёт в проекте годами. Нашёл похожее, но не подходящее — расширь существующее, не копируй рядом.

**Правило трёх.** Общее выносится, когда повторение случилось третий раз, а не когда кажется, что случится. Две похожие строки в двух местах дешевле неправильной общей абстракции.

**Базовые классы и общие слои.**

- Хорошо: один базовый класс с понятной ответственностью — `BaseRepository` с операциями чтения/записи, базовый layout, общая обёртка над HTTP
- Плохо: «BaseEntity», «BaseManager», куда со временем приезжает всё подряд. Такой класс перестаёт быть переиспользуемым и становится обязательным для всего
- База не знает о наследниках. Проверяет `instanceof` или содержит ветки под конкретный тип — это не база, а склад

Признаки, что пора выносить общее: третий одинаковый фрагмент; наследник переопределяет почти всё поведение базового (база неправильная — разбей); чтобы добавить вариант, приходится править общий класс во многих местах (переходи на композицию). Композиция предпочтительнее наследования.

## Слои

- Логика не живёт в UI и в обработчиках запросов: экран показывает, обработчик принимает запрос, решение принимает слой логики
- Слой логики не знает о фреймворке, БД и UI — он вызывается ими
- Доступ к данным — через репозиторий или слой данных, не SQL из компонента
- Зависимость направлена внутрь: UI → логика → данные. Обратных импортов нет

## Стиль

- Минимальный код, который решает задачу. Проще — лучше, чем «гибче»
- Никаких фич, флагов и параметров, которые никто не просил
- Обработка ошибок — для возможных сценариев, не «на всякий случай»
- Новое значение вместо правки существующего объекта, если проект не построен на мутации. Состояние живёт в одном месте
- Побочные эффекты — на границах (I/O, сеть, файлы), не в середине вычислений
- Внешний вход не доверенный: проверяется на границе, до попадания внутрь
- Ошибка не глотается молча: либо обработана, либо проброшена с контекстом
- Имя говорит, что значение значит, а не какого оно типа. Комментарий объясняет **почему**, когда это неочевидно из кода
- Форматирование решает форматер проекта, а не ты. Стиль файла не меняется под себя

## Чего не делать

- Не улучшать соседний код попутно, не рефакторить то, что не сломано
- Не удалять «мёртвый» код, который ты не создавал. Заметил — запиши в доску
- Не добавлять абстракцию под единственный случай
