# Коммиты

Читать перед первым коммитом в сессии. Инварианты — в `AGENTS.md`, здесь детали.

## Формат

```
type(scope): description
```

- **type**: `feat` | `fix` | `refactor` | `docs` | `test` | `chore` | `perf` | `build`
- **scope**: модуль или область — `auth`, `api`, `contacts`, `deps`. Не имя проекта
- **description**: императив, настоящее время, английский или русский — как принято в репозитории; одна строка; до 72 символов; без точки в конце

Хорошо:

```
feat(auth): добавить вход по одноразовой ссылке
fix(api): не падать на пустом списке контактов
refactor(export): вынести разделитель CSV в параметр
chore(deps): обновить vitest до 3.2
```

Плохо:

```
fixes            ← нет типа и описания
update           ← не говорит, что изменилось
feat: добавлена новая функциональность   ← не указан scope, размыто
feat: add X and fix Y and refactor Z     ← три изменения в одном коммите
```

Тело коммита — только если надо объяснить **почему**, а не что. Что видно в дифе, в теле не повторяется.

## Атрибуция

Коммит не должен содержать следов генерации:

- нет `Co-Authored-By: ...`
- нет `Generated with ...`, «Сгенерировано», `🤖`
- нет других trailer'ов, которых не поставил бы git сам

Автор и почта берутся из глобального конфига устройства. В репозитории `git config user.name` / `user.email` не выставляются, `--author` не используется, соавторы не добавляются.

## Что коммитить

- Один коммит — одно логическое изменение. Разная природа (фича + рефактор + формат) — разные коммиты
- Только то, что относится к задаче: `git add <пути>`, а не `git add -A` вслепую
- Перед коммитом посмотреть `git status` и `git diff` — не попало ли лишнее

Не коммитить никогда: `.env` и любые секреты, токены, ключи, `node_modules`, артефакты сборки, сгенерированные файлы, большие данные, `.zcode/state/`.

## Когда не коммитить

- Тесты падают
- Линтер находит ошибки (предупреждения — не повод)
- Задача не завершена и критерий успеха не выполнен
- Остались `blocker` или `high` на доске

В этих случаях возвращается причина, а не «почти готовый» коммит.

## Ветки и push

- Соло-проект: коммит в основную ветку
- Командный проект: ветка `feat/...` или `fix/...`, в main — через PR
- Push — только по прямой просьбе
- `--force` — только по явному подтверждению пользователя, никогда «чтобы прошло»
